# MQTT topics and payloads

Broker: Mosquitto 2. TLS on port 8883 in staging/prod; 1883 plain only in local dev.
Clients: driver app (while on duty), ESP32 trackers, simulator. Consumer: `ingestor` process.

## Topics
| Topic | Publisher | QoS | Retained | Purpose |
|---|---|---|---|---|
| `sc/v1/op/{operator_id}/veh/{vehicle_id}/gps` | vehicle | 0 | no | GPS pings (single or batch) |
| `sc/v1/op/{operator_id}/veh/{vehicle_id}/status` | vehicle | 1 | yes | `online`/`offline` (Last Will sets `offline`) |
| `sc/v1/op/{operator_id}/veh/{vehicle_id}/cmd` | backend | 1 | no | Commands to device (e.g. change ping interval) — Phase 2 |

- `{operator_id}` and `{vehicle_id}` are UUIDs.
- Topic version prefix `sc/v1` allows future payload changes.

## Access control
- Each vehicle has MQTT credentials issued at duty start (`POST /driver/duty` returns them) or provisioned for ESP32 trackers.
- ACL: a vehicle user may publish only to its own `.../veh/{vehicle_id}/gps` and `/status`, and subscribe only to its own `/cmd`.
- The ingestor user subscribes to `sc/v1/op/+/veh/+/gps` and `/status`.
- Implement with Mosquitto's dynamic security plugin or a password file + ACL file generated by the backend.

## GPS payload (JSON, UTF-8)
Single ping:
```json
{
  "v": 1,
  "ts": "2026-09-24T04:35:12.000Z",
  "lat": 28.5123,
  "lng": 77.3910,
  "spd": 8.4,
  "hdg": 132,
  "acc": 6.5,
  "bat": 71,
  "src": "app"
}
```
Batch (after offline period), max 500 pings, ordered by `ts`:
```json
{ "v": 1, "batch": [ {...}, {...} ] }
```
| Field | Type | Unit | Required |
|---|---|---|---|
| `v` | int | payload version | yes |
| `ts` | string ISO 8601 UTC | device GPS time | yes |
| `lat`, `lng` | float | degrees WGS84 | yes |
| `spd` | float | m/s | no |
| `hdg` | float | degrees 0–359 | no |
| `acc` | float | metres (horizontal accuracy) | no |
| `bat` | int | percent | no |
| `src` | string | `app`, `esp32`, `sim` | yes |

## Ingestor validation
- Drop pings with `acc` > 100 m, impossible jumps (> 50 m/s implied speed), or `ts` more than 24 h old or 2 min in the future (relative to `Clock`).
- Out-of-order pings are stored but do not move the "latest position" backwards.
- Latest position → Redis `veh:{vehicle_id}:pos` (hash: lat, lng, ts, spd, hdg) with TTL 10 min.
- Persist to `location_ping` in batches every 5 s.
- Publish internal event on Redis channel `ev:veh_pos:{operator_id}` for WebSocket fan-out.

## Ping intervals
| Situation | Interval |
|---|---|
| Moving (> 1 m/s) | 5 s |
| Stationary > 2 min | 30 s |
| Off duty | none |
| Offline | buffer locally, send as batch on reconnect |
The `/cmd` topic (Phase 2) can change intervals remotely.

## ESP32 tracker (optional hardware)
Same topics and payload with `src: "esp32"`. Firmware requirements: GNSS module, LTE/2G modem, TLS MQTT client, Last Will, local buffer of ≥ 30 min, OTA update. Detailed firmware spec is out of scope for Phase 1.

## HTTPS fallback
If MQTT is unreachable for 60 s, the app sends pings via `POST /driver/location` (batch, every 15 s) until MQTT reconnects.
